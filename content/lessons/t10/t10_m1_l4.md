# ADR и совместимость

- **Трек:** Архитектура и эксплуатация
- **Модуль:** Проектирование
- **Тип:** урок
- **ID:** `T10-M1-L4`

## Цель и критерий перехода

Объяснить контракт, инварианты, компромиссы и тесты; показать корректность на граничных случаях.

## Теория

Architecture Decision Record — короткая запись о важном архитектурном решении. Она содержит контекст, решение, альтернативы и последствия. ADR нужен не для каждого выбора имени переменной, а для решений, которые дорого менять или которые влияют на несколько компонентов. Например, модель владения, протокол обмена, формат данных, выбор хранилища или стратегия конкурентности.

Совместимость бывает исходной, бинарной, протокольной и совместимостью данных. Изменение публичной сигнатуры может ломать исходный код клиентов. Изменение layout класса может ломать ABI. Изменение сериализованного формата может сделать старые файлы нечитаемыми. Эти виды совместимости нужно проверять отдельно.

Версионирование помогает, но не исправляет плохую стратегию миграции. Для развёртывания несколькими версиями может потребоваться период, когда новая схема поддерживает и старый, и новый код. План отката должен учитывать, можно ли восстановить изменённые данные.

## Разобранный пример

```text
ADR-004: Хранилище прогресса

Контекст: состояние должно сохраняться после перезапуска.
Решение: SQLite на локальном устройстве.
Альтернативы: JSON-файл, удалённый PostgreSQL.
Последствия: транзакционная запись без серверной инфраструктуры.
Риски: ограничения конкурентного доступа и необходимость миграций схемы.
```

ADR фиксирует причину выбора, а не только название технологии. Если требования изменятся, запись помогает пересмотреть решение.

## Практика

1. **Задача:** Напиши ADR для выбора структуры хранения и объясни минимум две альтернативы.
   - **Критерий проверки:** Описаны контекст, решение, компромиссы и риски.
   - **Подсказка:** Не сравнивай технологии без требований.

2. **Задача:** Раздели возможные breaking changes на source, ABI и data-format compatibility.
   - **Критерий проверки:** Для каждого изменения есть способ обнаружения и план миграции.
   - **Подсказка:** Сборка клиентов не проверяет совместимость сохранённых файлов.

3. **Задача:** Смоделируй deployment, где старое и новое приложение читают одну схему.
   - **Критерий проверки:** Определён безопасный порядок расширения, переноса данных и удаления старого поля.
   - **Подсказка:** Рассмотри стратегию expand-and-contract.

## Граничные случаи

- Breaking change; смешанные версии; откат миграции.

## Типичные ошибки

- Записывать решение без альтернатив и последствий.
- Считать семантическое версионирование автоматической защитой.
- Предполагать, что любой database migration можно откатить без потери данных.

## Контрольные вопросы

1. Какое условие должно выполняться до вызова решения.
2. Что произойдёт на пустом или минимальном входе.
3. Какие тесты подтверждают корректность и какие ограничения остаются.
