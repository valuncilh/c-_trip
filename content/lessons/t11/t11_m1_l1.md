# Проект A — библиотека алгоритмов

- **Трек:** Проектная лаборатория
- **Модуль:** Интеграционные проекты
- **Тип:** project
- **ID:** `T11-M1-L1`

## Цель и критерий перехода

Объяснить контракт, инварианты, компромиссы и тесты; показать корректность на граничных случаях.

## Теория

Цель проекта — доказать, что ты умеешь проектировать библиотеку, а не только решать отдельную задачу. Выбери одну структуру данных для самостоятельной реализации, например кольцевой буфер, или набор алгоритмов графа. Сначала опиши публичный API и гарантии. Затем реализуй структуру, unit-тесты, benchmark и документацию.

Публичный API не должен раскрывать внутреннее представление без необходимости. Если реализуешь кольцевой буфер, определи поведение при полном и пустом состоянии, порядок элементов и семантику копирования. Если реализуешь алгоритмы графа, определи допустимый диапазон вершин, представление недостижимого результата и требования к весам рёбер.

Проект должен собираться через CMake из чистого checkout. Добавь install/export rules, чтобы другая маленькая программа могла подключить библиотеку без прямого доступа к исходникам реализации. Запускай тесты под ASan/UBSan, а затем измеряй производительность только для корректных реализаций.

## Разобранный пример

```text
include/course_core/ring_buffer.hpp
src/ring_buffer.cpp
tests/ring_buffer_test.cpp
benchmarks/ring_buffer_bench.cpp
examples/demo.cpp
CMakeLists.txt
README.md
```

Структура примерная. Для шаблонной реализации кода может быть больше в заголовке. Важно отделить публичный интерфейс, тесты, пример и benchmark.

## Практика

1. **Задача:** Опиши API, инварианты и сложность каждой операции до реализации.
   - **Критерий проверки:** Для пустого, полного и типового состояния поведение не двусмысленно.
   - **Подсказка:** Задай правила push/pop, отказа и переполнения.

2. **Задача:** Реализуй библиотеку и тесты на границы, дубликаты и ошибочные вызовы.
   - **Критерий проверки:** Тесты покрывают контракт, не только обычный сценарий.
   - **Подсказка:** Добавь тесты на ёмкость 0 и 1, если такой режим допускается.

3. **Задача:** Настрой CMake, CTest, sanitizers, установку и example consumer.
   - **Критерий проверки:** Другой проект подключает библиотеку по установочному интерфейсу.
   - **Подсказка:** Проверь чистую сборку отдельно от каталога исходников.

4. **Задача:** Сравни производительность с подходящей STL-структурой.
   - **Критерий проверки:** Есть baseline, методика, размеры и обсуждение компромиссов.
   - **Подсказка:** Не утверждай, что собственная реализация лучше без измерений.

## Граничные случаи

- Публичный API не раскрывает внутреннее представление.

## Типичные ошибки

- Писать код до определения семантики полного состояния.
- Сравнивать benchmark разных задач или конфигураций.
- Экспортировать внутренние заголовки как публичный API без необходимости.

## Контрольные вопросы

1. Какое условие должно выполняться до вызова решения.
2. Что произойдёт на пустом или минимальном входе.
3. Какие тесты подтверждают корректность и какие ограничения остаются.
