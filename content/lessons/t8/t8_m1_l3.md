# Транзакции, индексы и изоляция

- **Трек:** SQL и хранение данных
- **Модуль:** Реляционная модель
- **Тип:** урок
- **ID:** `T8-M1-L3`

## Цель и критерий перехода

Объяснить контракт, инварианты, компромиссы и тесты; показать корректность на граничных случаях.

## Теория

Транзакция объединяет несколько действий в одну логическую операцию. ACID описывает атомарность, согласованность, изоляцию и долговечность. Точная гарантия зависит от СУБД, движка, конфигурации и уровня изоляции. Нельзя считать, что один и тот же уровень изоляции во всех базах предотвращает одинаковые аномалии.

Индекс помогает быстрее найти строки, но требует памяти и обслуживания при записи. B-tree индекс часто подходит для точного поиска и диапазонов. Индекс на поле с низкой селективностью не всегда полезен. Планировщик выбирает план на основе статистики и оценки стоимости, поэтому используй `EXPLAIN` и измерения.

При конкурентных изменениях возможны lost update, блокировки и deadlock. Приложение должно определять, какие ошибки можно повторять. Повтор транзакции безопасен только при корректном откате и понимании идемпотентности операции.

## Разобранный пример

```sql
BEGIN;
UPDATE account SET balance = balance - 100 WHERE account_id = 1;
UPDATE account SET balance = balance + 100 WHERE account_id = 2;
COMMIT;
```

Сама последовательность недостаточна для законченной банковской операции. Нужно проверить существование счетов, достаточность средств, число изменённых строк, ограничения баланса и поведение при ошибке. Если один шаг не удался, транзакцию следует откатить.

## Практика

1. **Задача:** Смоделируй перевод между счетами и гарантируй отсутствие частичного результата.
   - **Критерий проверки:** При ошибке во втором update изменение первого не сохраняется.
   - **Подсказка:** Используй транзакцию и обработку всех ошибок.

2. **Задача:** Посмотри `EXPLAIN` для запроса до и после индекса.
   - **Критерий проверки:** Есть измерение на репрезентативном объёме данных.
   - **Подсказка:** Индекс добавляет стоимость записи и не гарантирует ускорение каждого запроса.

3. **Задача:** Опиши поведение двух одновременных обновлений одной записи.
   - **Критерий проверки:** Указан уровень изоляции и стратегия разрешения конфликта.
   - **Подсказка:** Рассмотри optimistic concurrency через поле version.

## Граничные случаи

- Lost update; phantom; retry после deadlock.

## Типичные ошибки

- Считать любой COMMIT успешным без проверки результата операции.
- Добавлять индексы без анализа плана.
- Автоматически повторять неидемпотентную транзакцию.
