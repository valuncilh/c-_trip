# Lock-free, futures и cancellation

- **Трек:** Конкурентность
- **Модуль:** Потоки и модель памяти
- **Тип:** урок
- **ID:** `T7-M1-L2`

## Цель и критерий перехода

Объяснить контракт, инварианты, компромиссы и тесты; показать корректность на граничных случаях.

## Теория

`future` и `promise` позволяют передать результат или исключение между задачами. Они удобны, когда важен результат асинхронной работы, но не заменяют архитектуру управления временем жизни и завершением задач. Нужна ясная стратегия ожидания, отмены и обработки исключений.

Lock-free алгоритмы требуют больше, чем заменить обычную переменную на atomic. CAS-циклы, ABA и безопасное освобождение памяти — сложные задачи. Поток может увидеть указатель, который уже был освобождён другим потоком. Даже если операция lock-free, она не обязательно быстрее mutex на конкретной нагрузке.

Cancellation обычно кооперативна. Поток или задача периодически проверяет stop request и завершает работу безопасным образом. Нельзя безоговорочно прерывать поток в произвольной точке, если это оставляет ресурсы или инварианты в неопределённом состоянии.

## Разобранный пример

```cpp
#include <future>

int compute() {
    return 6 * 7;
}

int main() {
    auto result = std::async(std::launch::async, compute);
    return result.get() == 42 ? 0 : 1;
}
```

`get()` получает результат и может повторно выбросить исключение, возникшее в асинхронной задаче. В рабочем коде также нужно определить поведение при отмене и ограничить время ожидания там, где это необходимо.

## Практика

1. **Задача:** Передай значение и исключение из фоновой задачи через future.
   - **Критерий проверки:** Оба пути — успех и ошибка — обработаны.
   - **Подсказка:** Попробуй задачу, которая выбрасывает исключение.

2. **Задача:** Добавь кооперативную остановку длительного worker.
   - **Критерий проверки:** Worker завершает работу в ограниченное время и освобождает ресурсы.
   - **Подсказка:** Проверяй stop request в безопасных точках.

3. **Задача:** Сравни mutex-структуру и lock-free вариант измерениями.
   - **Критерий проверки:** Есть нагрузка, корректность, анализ contention и цена поддержки.
   - **Подсказка:** Не называй алгоритм быстрым только на основании того, что он lock-free.

## Граничные случаи

- Use-after-free при reclamation; ABA; отмена во время shutdown.

## Типичные ошибки

- Считать lock-free синонимом без блокировок на уровне всей программы.
- Игнорировать reclamation и ABA.
- Не обрабатывать исключения из future.
