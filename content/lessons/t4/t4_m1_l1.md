# Единицы трансляции и линковка

- **Трек:** Сборка, зависимости и доставка
- **Модуль:** Сборочная система
- **Тип:** урок
- **ID:** `T4-M1-L1`

## Цель и критерий перехода

Объяснить контракт, инварианты, компромиссы и тесты; показать корректность на граничных случаях.

## Теория

Каждый `.cpp` файл после препроцессинга образует единицу трансляции. Заголовки обычно включают в несколько единиц трансляции, поэтому повторное определение обычной внешней функции может нарушить правило одного определения — ODR. Защита заголовка предотвращает повторное включение в одной единице трансляции, но сама по себе не исправляет любое нарушение ODR между разными файлами.

В заголовке обычно объявляют интерфейс, а в `.cpp` размещают определение. Шаблоны и некоторые `inline`-функции устроены иначе, потому что компилятору нужно видеть их определения в местах инстанцирования. Статическая библиотека обычно содержит объектные файлы, которые линкер включает в итоговый бинарник. Динамическая библиотека загружается отдельно во время запуска или явно программой.

ABI — соглашение на бинарном уровне о вызовах, именах символов, layout типов и других деталях. Изменение публичного layout класса или компилятора может влиять на бинарную совместимость, даже если исходники выглядят похожими.

## Разобранный пример


Объявление обычно помещают в заголовок, а определение — в отдельный `.cpp`. Ниже это показано как три файла. В реальном проекте `math.cpp` и `main.cpp` включают `math.hpp`, а компилятор получает оба `.cpp`.

```cpp
// math.hpp
#pragma once
int twice(int value);
```

```cpp
// math.cpp
int twice(int value) {
    return value * 2;
}
```

```cpp
// main.cpp
#include <iostream>

int twice(int value);

int main() {
    std::cout << twice(21) << '\n';
}
```

Это демонстрация структуры файлов. В реальном проекте включи `math.hpp` из обоих `.cpp`, добавь необходимые файлы в CMake и собирай их как отдельные единицы трансляции.


## Практика

1. **Задача:** Раздели проект на публичный заголовок, реализацию и приложение.
   - **Критерий проверки:** Определение не дублируется, приложение собирается из чистого каталога.
   - **Подсказка:** Добавь оба `.cpp` в сборочную команду.

2. **Задача:** Создай ошибку ODR и объясни, почему include guard её не всегда исправляет.
   - **Критерий проверки:** Различаются повторное включение и несколько определений в разных translation units.
   - **Подсказка:** Определи, где находится само определение функции.

3. **Задача:** Посмотри символы объектного файла через инструменты платформы.
   - **Критерий проверки:** Можешь найти имя экспортируемой функции и объяснить цель линкера.
   - **Подсказка:** На Linux подойдут `nm` и `readelf`.

## Граничные случаи

- Циклические include; несовпадающие определения; порядок линковки.

## Типичные ошибки

- Определять обычную внешнюю функцию в заголовке без корректной стратегии `inline` или шаблона.
- Считать `#pragma once` заменой пониманию ODR.
- Предполагать бинарную совместимость между любыми сборками.
