# Mutex, condition_variable и atomics

- **Трек:** Конкурентность
- **Модуль:** Потоки и модель памяти
- **Тип:** урок
- **ID:** `T7-M1-L1`

## Цель и критерий перехода

Объяснить контракт, инварианты, компромиссы и тесты; показать корректность на граничных случаях.

## Теория

Потоки выполняются конкурентно. Если два потока обращаются к одной памяти, хотя бы один доступ является записью и между ними нет подходящей синхронизации, возникает data race. В C++ это неопределённое поведение. `std::mutex` защищает критическую секцию, а RAII-обёртка `std::lock_guard` освобождает блокировку при выходе из области видимости.

`condition_variable` позволяет потоку ждать изменения состояния. Ожидание всегда должно быть связано с предикатом, потому что пробуждение может быть ложным, а уведомление не заменяет проверку условия. Атомики нужны для определённых видов совместного доступа, но выбор memory order требует понимания модели happens-before. Начинай с mutex и упрощай только при доказанной необходимости.

Дедлок появляется, когда потоки ждут ресурсы друг друга. Его можно предотвращать согласованным порядком блокировок, ограничением критических секций и подходящими средствами совместного захвата.

## Разобранный пример

```cpp
#include <mutex>

class Counter {
public:
    void increment() {
        std::lock_guard<std::mutex> lock(mutex_);
        ++value_;
    }

    int get() const {
        std::lock_guard<std::mutex> lock(mutex_);
        return value_;
    }

private:
    mutable std::mutex mutex_;
    int value_{0};
};
```

Обе операции используют один mutex. Если убрать блокировку только у `get`, чтение может конфликтовать с записью. Для корректности нужно синхронизировать и чтение, и запись.

## Практика

1. **Задача:** Найди гонку данных в двух потоках и исправь её.
   - **Критерий проверки:** TSan не показывает эту гонку в покрывающем сценарии.
   - **Подсказка:** Сначала попробуй mutex, прежде чем использовать atomics.

2. **Задача:** Реализуй producer-consumer с condition variable и предикатом.
   - **Критерий проверки:** Поток корректно просыпается, завершает работу и не теряет элементы.
   - **Подсказка:** Предикат проверяется под mutex и внутри `wait`.

3. **Задача:** Составь граф захвата двух mutex и найди цикл ожидания.
   - **Критерий проверки:** Есть стратегия, предотвращающая взаимную блокировку.
   - **Подсказка:** Одинаковый порядок захвата во всех путях уменьшает риск deadlock.

## Граничные случаи

- Lost wakeup; deadlock; starvation; неверный memory order.

## Типичные ошибки

- Ждать condition variable без предиката.
- Считать атомик автоматически достаточной синхронизацией всех связанных данных.
- Держать mutex дольше, чем нужно.
