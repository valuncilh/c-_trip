# Make и Ninja

- **Трек:** Сборка, зависимости и доставка
- **Модуль:** Сборочная система
- **Тип:** урок
- **ID:** `T4-M1-L3`

## Цель и критерий перехода

Объяснить контракт, инварианты, компромиссы и тесты; показать корректность на граничных случаях.

## Теория

Make читает правила сборки. Цель зависит от prerequisites и создаётся рецептом. Если зависимости новее результата, Make запускает рецепт. Поэтому точность графа зависимостей принципиальна. Если забыть указать заголовок или сгенерированный файл, инкрементальная сборка может оставить устаревший результат.

Ninja — минималистичная система выполнения графа сборки. В C++ проектах её часто используют как генератор CMake. На практике большинство правил проекта разумно описывать в CMake, а Ninja выбирать для быстрой инкрементальной сборки. Знать основы Make всё равно полезно для чтения сторонних проектов и простых автоматизаций.

Параллельная сборка запускает независимые цели одновременно. Если два правила одновременно записывают в один файл, возникает гонка. Граф должен корректно описывать зависимости и уникальные выходные файлы.

## Разобранный пример

```make
CXX ?= c++
CXXFLAGS ?= -std=c++20 -Wall -Wextra -Wpedantic

app: main.cpp math.cpp
	$(CXX) $(CXXFLAGS) main.cpp math.cpp -o app

.PHONY: clean
clean:
	rm -f app
```

Команды recipe начинаются с табуляции. В реальном проекте зависимость исполняемого файла должна включать заголовки, а лучше использовать CMake или генерацию depfile, чтобы не забыть include-зависимости.

## Практика

1. **Задача:** Напиши Makefile с отдельными объектными файлами.
   - **Критерий проверки:** Изменение одного `.cpp` не пересобирает весь проект без причины.
   - **Подсказка:** Опиши правила для `.o` и связь с соответствующими исходниками.

2. **Задача:** Собери один проект через CMake с генератором Makefiles и Ninja.
   - **Критерий проверки:** Оба способа создают одинаково работающую программу.
   - **Подсказка:** Используй отдельные build-каталоги для разных генераторов.

3. **Задача:** Сымитируй отсутствующую зависимость в графе сборки и найди дефект.
   - **Критерий проверки:** После изменения заголовка пересобираются зависимые цели.
   - **Подсказка:** Проверь depfile или список prerequisites.

## Граничные случаи

- Неверная зависимость; гонка параллельной сборки; stale generated file.

## Типичные ошибки

- Забывать табуляцию в recipe Make.
- Записывать один generated file из нескольких параллельных правил.
- Редактировать сгенерированный `build.ninja` вместо источника конфигурации.

## Контрольные вопросы

1. Какое условие должно выполняться до вызова решения.
2. Что произойдёт на пустом или минимальном входе.
3. Какие тесты подтверждают корректность и какие ограничения остаются.
