# Компиляция и линковка

- **Трек:** undefined
- **Модуль:** undefined
- **Тип:** урок
- **ID:** `T0-M1-L3`

## Цель и критерий освоения

Ты можешь собрать программу из нескольких единиц трансляции, объяснить разницу между ошибкой компиляции и ошибкой линковки, включить полезные предупреждения и выполнить чистую повторную сборку.

## Перед началом

- Уметь работать с файлами из терминала и пользоваться Git.

## Теория

### Зачем разбираться в этапах сборки

Когда проект состоит из одного короткого файла, команда компилятора кажется простой. В реальном проекте код разделён на заголовки и исходники, используется несколько библиотек, а ошибки могут возникать на разных этапах. Понимание этапа ошибки помогает выбрать правильное место поиска причины.

### Упрощённый путь от исходника до запуска

1. **Препроцессор** обрабатывает директивы вроде `#include` и макросы.
2. **Компилятор** проверяет программу по правилам языка и формирует машинный код в объектном файле (например, `main.o`).
3. **Линкер** соединяет объектные файлы и библиотеки, разрешает внешние символы и формирует исполняемый файл.
4. **Загрузчик ОС** при запуске загружает исполняемый файл и необходимые динамические библиотеки.

Конкретные инструменты могут объединять несколько этапов в одной команде, но логические границы остаются полезными.

### Объявление и определение

Объявление сообщает компилятору, что функция существует и какой у неё интерфейс. Определение содержит её тело. В C++ функцию можно вызвать из одного файла, если объявление видно, но на этапе линковки должна существовать подходящая реализация.

Ошибка вида «неизвестный тип» или «ожидался ;» обычно появляется на этапе компиляции. Ошибка `undefined reference` или `unresolved external symbol` обычно появляется на этапе линковки: реализация отсутствует в сборке, сигнатура не совпадает или библиотека не подключена.

### Заголовки и единицы трансляции

Каждый исходный `.cpp` обычно компилируется отдельно. Заголовок включается в текст единицы трансляции через `#include`. Обычный заголовок должен защищаться от повторного включения через `#pragma once` или include guards. Определение не-шаблонной функции обычно держат в одном `.cpp`, объявление — в заголовке.

### Предупреждения и чистая сборка

Предупреждение — не всегда ошибка стандарта, но часто сигнал о возможной проблеме: неиспользуемой переменной, подозрительном преобразовании или недостижимом коде. Флаги `-Wall -Wextra -Wpedantic` включают полезный набор предупреждений в GCC/Clang. Они не доказывают корректность, но помогают обнаружить часть дефектов.

Чистая сборка нужна, чтобы убедиться, что результат не зависит от старых объектных файлов. Не удаляй данные пользователя ради чистоты: удаляй только известный каталог сборки, например `build/`.

## Разобранный пример

### Исходный файл `main.cpp`

```cpp
#include <iostream>

int twice(int value);

int main() {
    std::cout << twice(21) << '\n';
}
```

### Реализация `math.cpp`

```cpp
int twice(int value) {
    return value * 2;
}
```

### Собери два исходника вместе

```bash
g++ -std=c++20 -Wall -Wextra -Wpedantic main.cpp math.cpp -o demo
./demo
```

Ожидаемый вывод:

```text
42
```

Если убрать `math.cpp` из команды сборки, объявление функции останется видимым, но её определение не попадёт в итоговый исполняемый файл. Компилятор может успешно обработать `main.cpp` отдельно, а линкер сообщит об отсутствующем символе.

## Практика

### Задача 1. Разнеси функцию на объявление в заголовке и определение в отдельном `.cpp`.

**Критерий проверки.** Чистая сборка проходит одной документированной командой; функция определена только в одном исходном файле.

> **Подсказка.** Добавь заголовок в main.cpp и не включай файл реализации через `#include`.

### Задача 2. Намеренно убери один исходный файл из команды сборки.

**Критерий проверки.** Ты определяешь, на каком этапе возникает ошибка и какой символ не найден.

> **Подсказка.** Сравни ситуацию с синтаксической ошибкой, например пропущенной точкой с запятой.

### Задача 3. Собери проект со строгими предупреждениями и исправь предупреждения, не отключая их массово.

**Критерий проверки.** Команда использует `-Wall -Wextra -Wpedantic`, причины предупреждений устранены.

> **Подсказка.** Предупреждение может говорить о ненужном коде или о преобразовании, которое не соответствует замыслу.

## Граничные случаи

- Определение функции не попало в команду сборки.
- Сигнатуры объявления и определения отличаются.
- Одна и та же не-шаблонная функция определена в нескольких единицах трансляции.
- Включён устаревший исполняемый файл после ошибки новой сборки.
- Заголовок включён несколько раз без защиты.

## Типичные ошибки

- Путать синтаксическую ошибку компиляции с отсутствующим символом на этапе линковки.
- Считать, что объявление функции заменяет её определение.
- Включать `.cpp` через `#include` вместо того, чтобы передавать его компилятору.
- Полагаться на старый исполняемый файл после неудачной сборки.
- Отключать все предупреждения, не разбираясь, что именно сообщил компилятор.
