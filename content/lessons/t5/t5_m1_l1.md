# Unit/integration/property tests

- **Трек:** Тестирование, отладка и качество
- **Модуль:** Проверка корректности
- **Тип:** урок
- **ID:** `T5-M1-L1`

## Цель и критерий перехода

Объяснить контракт, инварианты, компромиссы и тесты; показать корректность на граничных случаях.

## Теория

Тест должен проверять внешний контракт, а не повторять внутреннюю реализацию. Unit-тест локализует поведение небольшой единицы. Integration-тест проверяет взаимодействие нескольких компонентов. Regression-тест фиксирует ранее найденный дефект. Property-based тест задаёт общее свойство и проверяет его на множестве сгенерированных входов.

Хороший тест детерминирован, понятен и сообщает, что именно нарушилось. Избегай зависимости от времени, сети, порядка запуска и глобального состояния. Test double полезен, если настоящая зависимость медленная или недоступна, но подмена не должна симулировать детали, которые интерфейс не гарантирует.

Покрытие строк показывает, какой код был выполнен, а не доказательство корректности. Тесты должны проверять значения, ошибки, инварианты и границы.

## Разобранный пример

```cpp
#include <cassert>
#include <vector>

int first_or_zero(const std::vector<int>& values) {
    return values.empty() ? 0 : values.front();
}

int main() {
    assert(first_or_zero({}) == 0);
    assert(first_or_zero({7, 8}) == 7);
}
```

Это минимальная демонстрация. Для реального проекта используй тестовый фреймворк, чтобы тесты имели имена, хорошие сообщения об ошибках и интеграцию с CTest.

## Практика

1. **Задача:** Покрой публичную функцию позитивными, негативными и граничными тестами.
   - **Критерий проверки:** Есть пустой ввод, обычный случай и ошибочный вход.
   - **Подсказка:** Привяжи тесты к контракту.

2. **Задача:** Добавь regression-тест перед исправлением найденного бага.
   - **Критерий проверки:** Тест воспроизводит ошибку на старой версии и проходит после исправления.
   - **Подсказка:** Сначала добейся воспроизведения.

3. **Задача:** Сформулируй property для сортировки и проверь случайные массивы.
   - **Критерий проверки:** Результат упорядочен и содержит те же элементы, что вход.
   - **Подсказка:** Проверь отсортированность и сохранение мультимножества.

## Граничные случаи

- Тест зависит от времени/сети; проверен только happy path.

## Типичные ошибки

- Тестировать только счастливый путь.
- Проверять внутренние детали вместо контракта.
- Считать высокое покрытие достаточным доказательством качества.

## Контрольные вопросы

1. Какое условие должно выполняться до вызова решения.
2. Что произойдёт на пустом или минимальном входе.
3. Какие тесты подтверждают корректность и какие ограничения остаются.
