# Timeout, retry, idempotency, shutdown

- **Трек:** Архитектура и эксплуатация
- **Модуль:** Надёжность и безопасность
- **Тип:** урок
- **ID:** `T10-M2-L1`

## Цель и критерий перехода

Объяснить контракт, инварианты, компромиссы и тесты; показать корректность на граничных случаях.

## Теория

Сетевой вызов может зависнуть дольше, чем полезно пользователю. Timeout ограничивает ожидание конкретной операции. Лучше передавать дедлайн через цепочку вызовов, чтобы вложенные операции не каждая начинала полный новый таймаут. При повторе запроса должен учитываться оставшийся общий бюджет времени.

Retry помогает при временных ошибках, но способен усилить перегрузку. Ограничивай число попыток, добавляй backoff и jitter, повторяй только подходящие ошибки. Если клиент не знает, выполнилась ли операция на сервере до разрыва соединения, повтор может применить изменение дважды.

Идемпотентная операция даёт тот же итог при повторном применении. Для некоторых API используют idempotency key и сохраняют результат обработанного запроса. Graceful shutdown прекращает принимать новую работу, завершает или отменяет текущую по определённой политике и только после этого освобождает ресурсы.

## Разобранный пример

```text
request arrives
  -> validate idempotency key
  -> check stored result
  -> execute transaction if not processed
  -> store result with operation
  -> return stored result
```

Ключ идемпотентности должен быть связан с конкретной операцией и защищён от повторного использования с другим содержимым. Детали реализации зависят от модели хранения.

## Практика

1. **Задача:** Добавь bounded retry для временной ошибки сетевого запроса.
   - **Критерий проверки:** Есть максимум попыток и верхняя граница общего времени.
   - **Подсказка:** Не повторяй ошибки валидации и авторизации автоматически.

2. **Задача:** Смоделируй обрыв соединения после commit, но до ответа клиенту.
   - **Критерий проверки:** Повтор не выполняет платёж или другую неидемпотентную операцию второй раз.
   - **Подсказка:** Используй idempotency key или журнал операций.

3. **Задача:** Реализуй graceful shutdown для worker pool.
   - **Критерий проверки:** Новые задачи не принимаются после остановки, текущие обработаны по контракту.
   - **Подсказка:** Определи, ждём ли текущие задачи или отменяем их.

## Граничные случаи

- Retry storm; неизвестный результат commit; зависший shutdown.

## Типичные ошибки

- Повторять запрос бесконечно.
- Считать timeout доказательством, что сервер ничего не сделал.
- Освобождать ресурсы до завершения потоков, которые ими пользуются.
