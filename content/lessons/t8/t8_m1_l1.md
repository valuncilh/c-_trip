## Цель и критерий перехода

Объяснить контракт, инварианты, компромиссы и тесты; показать корректность на граничных случаях.

## Теория

Реляционная база хранит данные в таблицах, где строка представляет запись, а столбец — атрибут. Первичный ключ однозначно идентифицирует строку. Внешний ключ задаёт ссылку на другую таблицу и помогает не допустить «сиротских» записей. Ограничения `UNIQUE`, `CHECK` и `NOT NULL` переносят правила целостности в саму базу, где их сложно обойти случайным кодом приложения.

Нормализация помогает избегать аномалий обновления. Если имя преподавателя копируется в каждую строку посещения, изменение имени потребует обновить множество записей. Отдельная таблица преподавателей позволяет хранить факт в одном месте. Нормализация не означает, что всегда нужно создавать десятки таблиц. Схема должна отражать сущности и связи задачи.

`NULL` означает отсутствие или неизвестность значения, а не число ноль и не пустую строку. Сравнение с `NULL` через обычное `=` не работает ожидаемым образом. Используй `IS NULL` и учитывай трёхзначную логику.

## Разобранный пример

```sql
CREATE TABLE course (
    course_id INTEGER PRIMARY KEY,
    title TEXT NOT NULL UNIQUE
);

CREATE TABLE lesson (
    lesson_id INTEGER PRIMARY KEY,
    course_id INTEGER NOT NULL REFERENCES course(course_id),
    title TEXT NOT NULL,
    position INTEGER NOT NULL CHECK (position >= 0),
    UNIQUE (course_id, position)
);
```

Ограничение `UNIQUE (course_id, position)` запрещает две лекции с одной позицией в одном курсе. Правило сохранится даже если данные попытается записать другой клиент.

## Практика

1. **Задача:** Спроектируй схему для курса, модулей, уроков и прогресса учащегося.
   - **Критерий проверки:** У сущностей есть ключи и внешние ключи, дубликаты состояния прогресса запрещены.
   - **Подсказка:** Прогресс обычно уникален для пары user_id и lesson_id.

2. **Задача:** Найди аномалию обновления в денормализованной таблице и устрани её.
   - **Критерий проверки:** Факт хранится в одном авторитетном месте.
   - **Подсказка:** Раздели сущности и свяжи их ключами.

3. **Задача:** Добавь тесты для `NULL`, дубликатов и ссылок на отсутствующие записи.
   - **Критерий проверки:** База отклоняет некорректное состояние независимо от логики приложения.
   - **Подсказка:** Проверяй constraint violation.

## Граничные случаи

- Дубликаты; orphan rows; трёхзначная логика NULL.

## Типичные ошибки

- Полагаться только на валидацию приложения для целостности данных.
- Считать NULL равным нулю или пустой строке.
- Создавать foreign key без понимания жизненного цикла связанных данных.
