# Big O и амортизированный анализ

- **Трек:** undefined
- **Модуль:** undefined
- **Тип:** урок
- **ID:** `T2-M1-L1`

## Цель и критерий освоения

Ты можешь вывести оценку сложности из числа операций, отличить рост затрат от секунд на конкретном компьютере и объяснить разницу между худшей и амортизированной стоимостью.

## Перед началом

- Знать циклы и последовательные контейнеры.
- Уметь посчитать число повторений простого цикла.

## Теория

### Что описывает асимптотическая сложность

При росте объёма входа программа обычно выполняет больше операций и хранит больше данных. Асимптотический анализ описывает, как растут эти затраты при увеличении размера входа `n`. Он помогает сравнить алгоритмические подходы до того, как мы привяжемся к конкретному процессору.

`O(n)` обычно используют как асимптотическую верхнюю оценку порядка роста. `Θ(n)` означает, что рост ограничен сверху и снизу константными множителями для достаточно больших входов. Обозначение не задаёт время в миллисекундах и само по себе не сообщает, сколько памяти нужно программе.

### Считай операции, а не строки кода

Цикл, который проходит по `n` элементам и выполняет постоянное количество работы на каждом, имеет линейный рост `Θ(n)`. Два вложенных цикла, каждый из которых проходит все `n` элементов, выполняют примерно `n²` итераций, то есть имеют квадратичный рост `Θ(n²)`.

Если внутренний цикл выполняется только до текущего индекса, число повторений равно:

$$
0+1+2+\ldots+(n-1)=\frac{n(n-1)}{2}
$$

Старший член — `n²/2`. При большом `n` постоянная доля не меняет класс роста, поэтому оценка остаётся `Θ(n²)`. Но не следует автоматически считать любой двойной цикл квадратичным: границы могут быть разными, а внутренний цикл может сокращаться вдвое.

### Логарифмический рост

Если на каждой итерации размер задачи уменьшается в два раза, число итераций растёт примерно как `log₂(n)`. Например, бинарный поиск в отсортированной последовательности отбрасывает половину оставшегося диапазона после сравнения. Это и объясняет логарифмическую сложность числа шагов.

### Худший случай и фактическое время

Худший случай описывает максимум затрат среди допустимых входов заданного размера. Для линейного поиска он возникает, когда нужного элемента нет либо он находится в конце. Средний случай зависит от модели распределения входов. Константы, кэш, аллокации, ввод-вывод и оптимизации компилятора влияют на реальное время — Big O не заменяет измерение.

Для инженерного выбора сравнивай и теорию, и измерения на репрезентативных данных. Бенчмарк должен использовать одинаковую задачу, сборку, входы и методику прогонов, иначе сравнение может вводить в заблуждение.

### Амортизированная стоимость

У `std::vector::push_back` отдельная операция может потребовать перераспределения памяти и перемещения элементов, что занимает `O(n)`. Однако ёмкость вектора растёт рывками; при последовательности добавлений суммарная работа на большой серии позволяет получить амортизированную стоимость `O(1)` на одно добавление.

Амортизированное `O(1)` не означает, что каждая операция выполняется за константное время. Оно описывает среднюю стоимость операции на последовательности по подходящему анализу, а не вероятностное среднее по случайным данным. Если задержка отдельной операции критична, нужно учитывать редкое дорогое перераспределение и варианты управления ёмкостью.

## Разобранный пример

Сравни три типичных схемы:

```cpp
// Линейный проход: n итераций.
for (std::size_t i = 0; i < n; ++i) {
    consume(i);
}

// Все пары индексов i < j: n * (n - 1) / 2 итераций.
for (std::size_t i = 0; i < n; ++i) {
    for (std::size_t j = 0; j < i; ++j) {
        consume(i, j);
    }
}

// Повторное деление размера пополам: около log2(n) итераций.
for (std::size_t value = n; value > 1; value /= 2) {
    consume(value);
}
```

Если `n = 1000`, линейный цикл выполняет около 1000 итераций, цикл пар — 499 500, а деление пополам требует около 10 итераций. Эти числа описывают именно показанные схемы и постоянную работу внутри них, а не полное время любой программы с такими циклами.

## Практика

### Задача 1. Оцени сложность поиска элемента в неотсортированном векторе.

**Критерий проверки.** В худшем случае ты объясняешь, почему нужно проверить до n элементов.

> **Подсказка.** Рассмотри случай, когда элемент отсутствует.

### Задача 2. Выведи количество пар индексов §i < j§ для последовательности из n элементов.

**Критерий проверки.** Получена формула §n(n-1)/2§ и объяснено, почему её порядок роста квадратичный.

> **Подсказка.** Суммируй число элементов до каждого индекса: 0 + 1 + ... + (n-1).

### Задача 3. Измерь поиск на нескольких размерах входа.

**Критерий проверки.** Есть повторные запуски, наборы с найденным и отсутствующим элементом и описание компилятора/режима сборки.

> **Подсказка.** Не сравнивай один запуск с другим по миллисекундам без повторений.

### Задача 4. Объясни стоимость §push_back§ у std::vector.

**Критерий проверки.** Ты различаешь амортизированную стоимость добавления и худшую стоимость отдельного перераспределения.

> **Подсказка.** Представь серию добавлений и редкие расширения ёмкости.

## Граничные случаи

- Пустой или очень маленький вход, когда константы важнее асимптотики.
- Внутренний цикл имеет изменяющуюся границу.
- В худшем случае поиск не находит элемент.
- Редкое перераспределение памяти у вектора.
- Бенчмарк отличается компилятором, данными или режимом сборки.

## Типичные ошибки

- Путать O(n) со временем в миллисекундах.
- Оценивать алгоритм по числу строк, а не по числу операций.
- Считать любой вложенный цикл квадратичным, не изучив границы.
- Утверждать, что §push_back§ всегда стоит O(1) в худшем случае.
- Использовать один бенчмарк-прогон как доказательство превосходства алгоритма.
