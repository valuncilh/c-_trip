## Теория

### Класс объединяет состояние и контракт

Класс описывает тип, который объединяет данные и операции над ними. Объект — конкретный экземпляр этого типа. Публичные методы задают интерфейс, а приватные поля позволяют классу контролировать собственное состояние.

**Инвариант класса** — условие, которое должно быть истинным для каждого полностью созданного объекта перед и после каждого публичного метода. Например, у диапазона измерений нижняя граница не должна быть больше верхней. Если любой публичный метод может случайно нарушить это условие, класс не контролирует свой контракт.

### Конструктор отвечает за начальное состояние

Конструктор создаёт объект и должен установить его инвариант. Поля следует инициализировать в списке инициализации, а не присваивать им значения после создания. Так поля сразу конструируются нужным образом, и это особенно важно для ссылок, const-полей и типов без конструктора по умолчанию.

Если конструктор обнаружил недопустимые параметры, он может сообщить об ошибке, например бросить исключение. Если конструирование не завершилось, деструкторы уже успешно созданных полей вызываются автоматически. Нельзя полагаться на методы обычного объекта, пока его конструктор не завершился успешно.

### Время жизни и деструктор

Время жизни объекта — промежуток, когда объект считается существующим и к нему можно обращаться по правилам языка. Локальные автоматические объекты уничтожаются при выходе из своей области видимости. При уничтожении объекта вызывается деструктор, а затем уничтожаются его нестатические поля в обратном порядке инициализации.

Ресурс — это не только память. Им может быть файл, сокет, блокировка, дескриптор устройства или транзакция. В C++ идея **RAII** связывает владение ресурсом со временем жизни объекта: конструктор захватывает ресурс, а деструктор освобождает его. Это позволяет безопаснее переживать обычный выход из функции и исключения.

### Rule of Zero

Если поля класса уже используют типы, которые самостоятельно управляют своими ресурсами, как `std::string`, `std::vector` и `std::unique_ptr`, обычно не нужно писать собственные деструктор, конструктор копирования и оператор присваивания. Компилятор может сгенерировать корректное поведение из операций полей. Этот подход называют Rule of Zero.

Если класс непосредственно владеет сырым ресурсом, копирование по умолчанию может оказаться неправильным: например, две копии могут считать, что обе отвечают за освобождение одного и того же ресурса. Тогда нужно определить семантику копирования и перемещения — либо заменить сырой ресурс RAII-объектом.

### Копирование, перемещение и const-методы

Копирование создаёт независимый объект согласно правилам типа. Перемещение позволяет передать ресурсы новому объекту без обязательного дорогостоящего копирования их содержимого; само по себе слово move не гарантирует конкретную скорость. Дизайн копирования должен сохранять инварианты, а не копировать внутреннее представление любой ценой.

Метод с квалификатором `const` обещает не менять наблюдаемое состояние объекта через обычные поля. Такие методы могут вызываться для const-объектов. Не делай поля публичными только ради удобства: это позволяет внешнему коду нарушить инвариант в обход методов класса.

## Разобранный пример

```cpp
#include <stdexcept>
#include <string>
#include <utility>

class Device {
public:
    Device(std::string name, int channel)
        : name_(std::move(name)), channel_(channel) {
        if (name_.empty()) {
            throw std::invalid_argument("name must not be empty");
        }
        if (channel_ < 0) {
            throw std::invalid_argument("channel must be non-negative");
        }
    }

    const std::string& name() const { return name_; }
    int channel() const { return channel_; }

private:
    std::string name_;
    int channel_;
};
```

Инвариант класса `Device`: имя не пустое, номер канала неотрицательный. Все поля приватны; конструктор сначала инициализирует их, затем проверяет контракт и при нарушении сообщает об ошибке.

Класс не требует пользовательского деструктора: `std::string` освобождает собственную память. Если конструктор бросит исключение, уже сконструированное поле `name_` корректно уничтожится автоматически.

## Практика

### Задача 1. Спроектируй класс §Range§, у которого нижняя граница не выше верхней.

**Критерий проверки.** Некорректный объект нельзя создать через публичный интерфейс; тесты проверяют равные и переставленные границы.

> **Подсказка.** Сформулируй инвариант, затем обеспечь его в конструкторе.

### Задача 2. Объясни, почему класс, состоящий из §std::string§ и §std::vector<int>§, обычно не требует собственного деструктора.

**Критерий проверки.** В ответе объяснено, что члены владеют своими ресурсами и уничтожаются вместе с объектом.

> **Подсказка.** Оба типа уже управляют памятью и временем жизни своих элементов.

### Задача 3. Найди в учебном классе сырой владеющий указатель и предложи вариант с RAII.

**Критерий проверки.** Не возникает двойного освобождения, утечки или неясного владения.

> **Подсказка.** Рассмотри §std::vector§ или §std::unique_ptr§ вместо ручного §new/delete§.

### Задача 4. Добавь const-методы чтения к классу и опиши, какие операции должны оставаться приватными.

**Критерий проверки.** Чтение доступно через const-объект; инвариант нельзя обойти прямым изменением поля.

> **Подсказка.** Публичный интерфейс должен выражать разрешённые операции, а не раскрывать представление.

## Граничные случаи

- Некорректные параметры конструктора.
- Исключение во время конструирования.
- Копирование объекта, который владеет ресурсом.
- Перемещение и состояние исходного объекта.
- Вызов методов после окончания времени жизни.
- Попытка изменить состояние через const-объект.

## Типичные ошибки

- Делать все поля публичными и позволять внешнему коду нарушать инвариант.
- Инициализировать поле по умолчанию, а затем присваивать ему значение в теле конструктора без необходимости.
- Писать собственный деструктор, не понимая последствий для копирования и перемещения.
- Предполагать, что исключение из конструктора оставляет полностью созданный объект.
- Хранить ресурс в сыром указателе без ясного владельца и правила освобождения.
- Считать, что std::move сам по себе перемещает объект или гарантирует ускорение.
