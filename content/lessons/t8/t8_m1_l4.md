# SQL из C++ и миграции

- **Трек:** SQL и хранение данных
- **Модуль:** Реляционная модель
- **Тип:** урок
- **ID:** `T8-M1-L4`

## Цель и критерий перехода

Объяснить контракт, инварианты, компромиссы и тесты; показать корректность на граничных случаях.

## Теория

Запросы с пользовательскими значениями должны использовать параметризацию. Нельзя строить SQL конкатенацией строк с вводом пользователя. Prepared statements отделяют текст запроса от значений и помогают предотвратить SQL injection.

Граница транзакции должна совпадать с логической операцией приложения. Не держи транзакцию открытой во время долгих сетевых вызовов без веской причины. Пул соединений ограничивает количество одновременно открытых соединений, но требует корректного возврата соединения и очистки состояния после ошибки.

Миграция изменяет схему базы между версиями приложения. Важно понимать, совместима ли новая схема со старой версией приложения во время rolling deployment. Откат не всегда прост: после удаления столбца или преобразования данных прежнюю схему может быть невозможно восстановить без резервной копии.

## Разобранный пример

```sql
-- Шаблон запроса с параметром, синтаксис зависит от драйвера.
SELECT lesson_id, completed
FROM lesson_progress
WHERE user_id = ? AND lesson_id = ?;
```

Символ `?` — пример placeholder для некоторых драйверов. В конкретном API используй правильный синтаксис параметра и методы связывания значений.

## Практика

1. **Задача:** Реализуй слой репозитория с параметризованными запросами.
   - **Критерий проверки:** В запрос не конкатенируются пользовательские значения.
   - **Подсказка:** Отдели интерфейс репозитория от конкретного драйвера.

2. **Задача:** Создай миграции из первой схемы во вторую и проверь данные.
   - **Критерий проверки:** Переход повторяем, версии схемы понятны, ограничения не нарушены.
   - **Подсказка:** Выполняй миграцию в транзакции, если СУБД и операция это поддерживают.

3. **Задача:** Смоделируй обрыв соединения во время записи и повтор операции.
   - **Критерий проверки:** Нет двойного применения неидемпотентного действия.
   - **Подсказка:** Подумай о ключе идемпотентности или журнале операции.

## Граничные случаи

- SQL injection; разрыв после commit; повтор неидемпотентной операции.

## Типичные ошибки

- Конкатенировать ввод в SQL.
- Повторять запись после неизвестного результата COMMIT без модели идемпотентности.
- Забывать закрывать или возвращать соединение в пул.

## Контрольные вопросы

1. Какое условие должно выполняться до вызова решения.
2. Что произойдёт на пустом или минимальном входе.
3. Какие тесты подтверждают корректность и какие ограничения остаются.
