## Теория

### Зачем нужен контроль версий

Git хранит историю изменений проекта. Его задача — не только иметь резервную копию, но и позволять объяснить, почему изменился файл, сравнить два состояния, вернуться к предыдущему состоянию и вести несколько независимых линий работы.

### Три состояния файла

Упрощённая модель Git состоит из трёх частей:

- **Рабочее дерево** — файлы, которые ты сейчас видишь и редактируешь.
- **Индекс (staging area)** — конкретные изменения, выбранные для следующего коммита.
- **История** — уже созданные коммиты, связанные родительскими коммитами.

`git add` копирует выбранное состояние изменений в индекс. Это не коммит и не отправка на сервер. `git commit` создаёт локальную точку истории из того, что находится в индексе. Поэтому перед коммитом полезно проверять и `git diff`, и `git diff --cached`: первый показывает изменения рабочего дерева, второй — подготовленные изменения.

### Коммиты, ветки и удалённый сервер

Коммит — снимок подготовленного состояния с сообщением. Хороший коммит отвечает на вопрос «какое одно логическое изменение внесено?». Небольшие коммиты проще ревьюить и откатывать.

Ветка — имя, указывающее на текущий коммит. Она не является отдельной копией всех файлов. Новую работу удобно начинать в отдельной ветке, чтобы не смешивать её с основной линией. `git push` отправляет коммиты на удалённый сервер; локальный коммит сам по себе не опубликован.

### Конфликт слияния

Когда Git не может автоматически совместить изменения двух веток, он оставляет конфликтные маркеры. Не выбирай сторону наугад: прочитай обе версии, восстанови нужное поведение и удали маркеры. После разрешения выполни тесты, потому что разрешённый синтаксически конфликт всё ещё может повредить логику.

### Что не следует коммитить

Временные файлы сборки, исполняемые файлы, локальные настройки IDE и секреты обычно не должны попадать в репозиторий. `.gitignore` помогает игнорировать известные пути, но не удаляет файл, уже добавленный в индекс. Если секрет попал в историю, простое удаление из текущего файла не делает его безопасным: секрет следует отозвать или заменить.

## Разобранный пример

### Посмотри состояние до изменений

```bash
git status
git diff
git diff --cached
```

### Подготовь один файл и проверь индекс

```bash
git add src/main.cpp
git diff --cached
git commit -m "Add command-line entry point"
```

Имя файла — пример: используй путь, который существует в твоём проекте. Если команда `git diff --cached` ничего не показывает, в индекс не попали изменения, и коммит может оказаться пустым.

### Создай отдельную ветку

```bash
git switch -c docs/terminal-guide
git status
```

Перед коммитом читай diff, а не только сообщение редактора или название файла. Если нужно убрать файл из индекса, оставив рабочую копию, используй `git restore --staged path/to/file` и повторно проверь статус.

## Практика

### Задача 1. Создай репозиторий и добавь `.gitignore`, игнорирующий каталог `build/`.

**Критерий проверки.** После сборки `git status` не показывает содержимое каталога build как новые файлы.

> **Подсказка.** Если сборочные файлы уже были добавлены в индекс, одного .gitignore недостаточно.

### Задача 2. Измени два файла, но добавь в индекс только один. Покажи, чем отличаются `git diff` и `git diff --cached`.

**Критерий проверки.** В индексе находится только запланированное изменение; второй файл не попадёт в следующий коммит.

> **Подсказка.** Используй `git add path/to/file` вместо безусловного добавления всего дерева.

### Задача 3. Создай ветку, измени один файл и подготовь коммит с осмысленным сообщением.

**Критерий проверки.** Ветка отличается от исходной историей коммитов, а diff коммита содержит только относящееся к сообщению изменение.

> **Подсказка.** Перед коммитом проверь `git status` и `git diff --cached`.

### Задача 4. Намеренно создай конфликт в тестовом репозитории и разреши его.

**Критерий проверки.** Маркеров конфликта не осталось, история корректна, тесты проходят.

> **Подсказка.** Сначала прочитай обе версии, затем запусти поиск маркеров `<<<<<<<` и `>>>>>>>`.

## Граничные случаи

- Изменения уже находятся в индексе до начала работы.
- Файл был добавлен до появления правила .gitignore.
- Удалённая ветка содержит новые коммиты.
- Конфликт касается поведения программы, а не только форматирования.
- В коммит случайно попал файл с секретом.

## Типичные ошибки

- Думать, что `git add` публикует файл на сервере.
- Выполнять коммит, не просматривая подготовленный diff.
- Добавлять все файлы без проверки и включать случайные бинарники.
- Считать, что `.gitignore` удаляет ранее отслеживаемые файлы.
- Разрешать конфликт, оставляя маркеры или выбирая сторону без проверки тестами.
